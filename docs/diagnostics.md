# Диагностика: что именно измеряет приложение

Документ объясняет, какие цифры считаются доказанными, какие — признаком, а какие
приложение принципиально измерить не может. Это важнее красивых чисел: неверно
подписанный замер хуже отсутствия замера.

## 1. Три разные «задержки»

| Величина | Как измеряется | Что доказывает | Чего не доказывает |
|---|---|---|---|
| **TCP-доступность узла** | `connect()` до `host:port`, медиана 3 попыток, DNS вне замера | адрес доступен, порт открыт | что VPN-протокол работает, что логин принят, что туннель пропускает трафик |
| **Реальная задержка** | HTTP GET `generate_204` через активное подключение, первый запрос — разогрев, дальше медиана по keep-alive | весь путь работает: протокол, выход сервера, DNS, TLS | скорость канала |
| **Скорость** | 2–8 параллельных соединений, срезы по 100 мс | пропускная способность до сервера замера | скорость конкретного сайта |

Методика реальной задержки взята у **v2rayNG / v2rayN / NekoBox / Hiddify**: они
запускают ядро с конкретным outbound и меряют HTTP-запрос сквозь него. Приложение
не может запустить чужое ядро, поэтому меряет сквозь **системный** туннель — то
есть проверяет тот конфиг, который пользователь включил в своём клиенте.

### Почему раньше у всех узлов были одинаковые миллисекунды

Когда VPN включён в режиме TUN, TCP-соединение принимает **локальный VPN-клиент**,
а не сервер. Рукопожатие завершается за 1–5 мс у любого адреса, включая мёртвый.
Теперь:

1. проба узла идёт через **физическую сеть в обход VPN** — сокет и DNS
   привязываются к Wi-Fi/LTE (`Network.getSocketFactory()`, `Network.getAllByName()`);
2. если система не даёт прямой доступ (постоянный VPN, lockdown), число **не
   выдумывается** — приложение объясняет причину;
3. локальный ответ (`< 5 мс` при маршруте через VPN) помечается и не попадает
   в рейтинг узлов.

## 2. Что Android разрешает знать о чужом VPN

Можно:

- факт системного VPN (`TRANSPORT_VPN`);
- **идёт ли через туннель трафик именно нашего приложения** — это отдельный факт;
- пакет и название VPN-клиента (`NetworkCapabilities.getOwnerUid()` +
  `<queries><intent android:name="android.net.VpnService">` в манифесте);
- always-on VPN и режим lockdown (`Settings.Secure`);
- список установленных VPN-клиентов;
- внешний IP приложения и внешний IP физической сети.

Нельзя:

- прочитать, какой **конфиг** выбран внутри v2rayNG/Happ/NekoBox — Android не
  раскрывает состояние другого приложения;
- переключить конфиг в чужом клиенте.

Поэтому активный узел определяется двумя честными способами и помечается как
предположение, пока пользователь не подтвердил:

1. **память выбора**: пара «клиент + выходной IP» → узел, который пользователь
   выбрал в прошлый раз;
2. **совпадение IP**: выходной IP равен адресу сервера узла из последней
   DNS-резолюции.

### Раздельный туннель (per-app proxy)

Если VPN включён, но наше приложение исключено из проксирования, Android отдаёт
ему обычную сеть. Раньше это выглядело как «VPN выключен», и проверки сайтов
показывали российский интернет вместо туннеля. Теперь приложение:

- показывает отдельное предупреждение «VPN включён, но приложение идёт мимо туннеля»;
- умеет доказать это сравнением IP двух маршрутов (кнопка «Проверить, идёт ли
  трафик через VPN»);
- подсказывает добавить «ПульсСети» в проксируемые приложения в клиенте.

## 3. Проверка сайтов

Порядок: HTTP-запрос нативным стеком (без CORS) → главная страница, если адрес
проверки не открылся → повтор → TCP-проба порта. Результат честно различает:

- «страница открыта» — получено своё содержимое;
- «адрес ответил · HTTP 403/404» — сервер жив, но страница не отдана;
- «TCP-порт отвечает, но HTTP-ответ не получен» — маршрут есть, страница режется;
- «нет соединения» — маршрут не подтверждён;
- «эта сборка не умеет проверять сайты» — отказ моста, а не блокировка сайта.

Последний пункт появился после реального инцидента: JS вызывал
`ApkUpdater.httpProbe()`, а в Java метода не было, и **любой** сайт в APK получал
«не отвечает». Теперь `tests/native-contract.test.ts` сверяет каждый вызываемый
метод с `@PluginMethod` в Java и падает при расхождении.

## 4. Подтверждения приложений

Отзыв привязан к маршруту: `node_key` (`vpn:<id>` или `direct`) + выходной IP +
VPN-клиент. Правила:

- отзыв ищется **по выбранному узлу**; если выходной IP сменился (обычное дело у
  VPN-провайдеров), карточка остаётся зелёной с пометкой «IP изменился»;
- для прямого подключения смена IP означает другую сеть — отзыв не переносится;
- отзыв другого узла с тем же IP показывается как совпадение по IP, но не
  добавляет этому узлу голос в рейтинге;
- смена системного `sequence` (переподтверждение сети при открытии другого
  приложения) больше не отменяет маршрут: сравниются транспорт, VPN, клиент и IP.

## 5. Замер скорости

Методика повторяет **Ookla Speedtest**:

1. выбор ближайшего доступного сервера по задержке;
2. разогрев небольшим объёмом — оценка канала задаёт число соединений (2–8) и
   размер куска (1–16 МБ);
3. загрузка ~10 с параллельными соединениями, семплер каждые 100 мс;
4. отдача ~8 с; байты учитываются **после ответа сервера**, а не по записи в сокет;
5. интервалы группируются в 20 срезов, отбрасываются 10% самых быстрых и 30% самых
   медленных, остальные усредняются (это отсекает slow start и всплески буфера);
6. если данных мало, результат помечается «приблизительно», а не выдаётся за точный.

Данные несжимаемые: иначе замер показал бы скорость компрессора, а не канала.

Точки замера, в порядке приоритета:

1. свой сервер «ПульсСети» (`/api/speed/ping|down|up`) — без чужих лимитов;
2. общий сервер сообщества (те же пути в Cloudflare Worker);
3. публичные точки Cloudflare `speed.cloudflare.com/__down|__up` — работают без
   ключа, но отвечают `429` при частых замерах; приложение объясняет это и
   предлагает подключить свой сервер.

Расход трафика: до ~120 МБ на загрузку и ~40 МБ на отдачу за один замер.

### Сравнение конфигов подписки

Каждый замер сохраняется с маршрутом: тип сети, VPN-клиент, выходной IP, выбранный
конфиг. Приложение считает **медиану** по конфигу и сравнивает с прямым
подключением на том же типе сети:

- ≥ 85% — «почти без потерь»;
- 50–85% — «теряет N% скорости»;
- < 50% — «сильно ограничивает»;
- нет прямого замера — вывод о потерях не делается.

Отдельно определяется «потолок»: скорость держится у круглого значения
(10/25/50/100/250/500/1000 Мбит/с) почти без колебаний — признак тарифного лимита
или шейпера сервера.

Порядок действий: замерить без VPN → включить конфиг в клиенте → замерить, выбрав
его в списке → повторить для остальных. Приложение не переключает чужой VPN.

## 6. Как отчёты о сбоях доходят до владельца

1. **Общий сервер (рекомендуется).** Владелец разворачивает Worker + D1 workflow
   «Deploy community API» (два секрета GitHub) или свой сервер из этого
   репозитория в Docker. Адрес вводится на вкладке «Сбои» → «Подключить сервер».
   Дальше отчёты уходят автоматически при открытии вкладки, раз в 60 секунд и по
   кнопке обновления. Повторная доставка идемпотентна, правки доводятся PATCH,
   удаления оставляют tombstone.
2. **Ссылка-приглашение.** Владелец копирует ссылку вида
   `…/#community=https%3A%2F%2Fapi.example` и отправляет участникам: адрес
   подставляется сам, остаётся нажать «Проверить и подключить».
3. **Обмен пакетом без сервера.** Вкладка «Сбои» → «Обмен»: выгрузка JSON-пакета
   и загрузка чужого. Слияние по `client_id`, побеждает свежая правка, удалённые
   отчёты не воскрешают, ключи устройства и голоса в пакет не попадают.
